# `dmg-engine` 初步调研记录

> 调研日期：2026-10-08  
> 调研范围：`dmg-engine/` 目录中的 README、核心引擎、CLI、输入快照、流派包及验证工具。  
> 文档性质：基于当前代码阅读的初步技术调研，不替代后续对游戏机制和产品设计的讨论。

## 1. 调研结论摘要

当前 `dmg-engine` 已经是一个可运行的“期望伤害计算核心”，并且与完整工具的 DPS 计算环节高度相关。

但它目前更准确地说是：

> **基于特定流派包和特定战斗轴的期望伤害计算器，而不是完整的装备调律分析工具。**

它可以承担以下职责：

- 读取一个流派包；
- 读取一组已经汇总好的面板/属性输入；
- 按技能轴计算每次施放伤害；
- 计算总伤害；
- 计算 ADPS；
- 计算毕业率；
- 在修改输入后重新计算并比较结果。

它目前不能直接承担以下职责：

- 管理 8 个装备部位；
- 保存装备实体；
- 管理初始词条、4 条调律词条和定音词条；
- 根据部位和等阶校验词条；
- 将固定属性、半固定属性和装备词条汇总成完整角色属性面板；
- 由用户直接选择流派；
- 执行单件装备替换；
- 搜索最优 8 件装备组合；
- 输出每个装备词条对最终 DPS 的解释性贡献。

初步判断是：

> 现有引擎可以作为完整产品的计算内核，但需要在它上方增加“角色属性模型”和“装备解析/比较层”。

```python
jisuanZhou(liupaiBao, shuru, baoliuMingxi=False)
```

命令行入口位于 `engine/cli.py`：


README 中还展示了作为 Python 库调用的方式：先读取流派包和输入 JSON，再调用 `jisuanZhou()`。

## 5. 当前计算模型

README 中记录的总体模型是：

```text
总伤 = Σ 每一次施放的伤害
ADPS = 总伤 / 战斗时间
毕业率 = ADPS / 毕业率基准
```

### 5.1 实际攻击推导

实际属性不是直接使用输入值，而是先进行推导：

```text
实际外功 = (面板外功 + 食物加成) × 套装乘区
实际属性 = (面板属性 + 生效无相攻击) × 套装乘区
```

代码中还对“最小值大于最大值”的情况做了特殊处理。

### 5.2 五分支伤害

一次施放伤害由以下部分相加：

- 外功分支；
- 鸣金分支；
- 裂石分支；
- 牵丝分支；
- 破竹分支。

基本形式：

```text
分支伤害 =
  (即时攻击 × 倍率 + 固伤)
  × (1 + 穿透)
  × (1 + 伤害加成)
```

其中只有当前流派的生效武学属性分支使用对应的属性倍率和属性固伤特殊系数。

### 5.3 四种状态

每次技能施放按四种状态进行期望加权：

- 会心；
- 会意；
- 普通；
- 擦伤。

取攻击档位的方式为：

- 会心：小值和最大值取中值；
- 会意：取最大值；
- 普通：取中值；
- 擦伤：取最小值。

### 5.4 穿透

穿透净额：

```text
输入穿透 - 目标对应抗性 + 技能穿透 + 增益穿透
```

规则：

- 净额大于 0：按正穿透效果计算；
- 净额不大于 0：按另一种负穿透效果计算。

README 记录的常量为：

- 正穿透效果：每点 `0.5%`；
- 负穿透效果：每点 `1%`。

### 5.5 结算施放

结算施放先计算：

```text
结算伤害 = 范围内施放伤害总和 × 结算比例 × (1 + 结算增伤)
```

代码采用两遍处理：

1. 先计算全部普通技能施放；
2. 再计算结算施放。

这是为了允许结算范围引用时间上更晚的施放。

## 6. 当前输出

核心输出位于 `engine/core.py` 的 `jisuanZhou()`。

默认输出包括：

```json
{
  "liupaiBaoBianhao": "...",
  "adps": 0,
  "biyelv": 0,
  "zongshang": 0
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `liupaiBaoBianhao` | 使用的流派包编号 |
| `zongshang` | 总伤害 |
| `adps` | 总伤害 / 战斗时间 |
| `biyelv` | ADPS / 流派包中的毕业率基准 |

传入 `baoliuMingxi=True` 后，还会输出：

- 每次施放序号；
- 技能名称；
- 施放伤害；
- 会心期望；
- 会意期望；
- 普通期望；
- 擦伤期望；
- 四种状态占比；
- 结算范围伤害。

CLI 默认输出会对结果进行四舍五入，并可用 `--mingxi` 附带逐次施放明细。

## 7. 当前结果验证情况

README 记录了四个流派包的重算结果：

| 流派包 | 引擎与原表相对误差 | 逐次施放 |
|---|---:|---:|
| 破竹风 3.1 | `1.85e-15` | 0 个不一致 |
| 破竹尘 3.1 | `1.00e-15` | 0 个不一致 |
| 牵丝玉 3.2 | `0` | 0 个不一致 |
| 破竹樽 3.5 | `2.20e-15` | 0 个不一致 |

这说明当前引擎能够复现现有 Excel 计算器的结果。

但需要区分两种结论：

1. **代码实现结论：** 引擎重构结果与现有 Excel 一致；
2. **游戏真实机制结论：** Excel 本身使用的机制、默认值和场景假设是否完全符合游戏实际，需要另行验证。

因此后续不能仅凭“与 Excel 一致”就认为所有游戏条件下的 DPS 结论都已经被证明正确。

## 8. 与完整产品设想的一致部分

### 8.1 DPS 作为装备比较标准

当前引擎可以完成：

```text
一组最终属性输入 + 固定战斗轴 → ADPS
```

如果外部负责将装备替换前后的属性面板转换为引擎输入，那么引擎就可以直接用于比较：

```text
旧装备面板 → ADPS_old
新装备面板 → ADPS_new
ADPS_new > ADPS_old → 新装备更优
```

因此，现有引擎的计算方向与产品设想一致。

### 8.2 流派配置与角色输入分离

当前已有 `packages/` 和 `inputs/` 的分离，这与完整产品需要的数据分层方向一致：

```text
流派/版本/轴/目标等规则 → 流派包
玩家当前属性 → 输入快照
```

### 8.3 支持修改输入后重新计算

README 中给出了修改一个增伤输入后重新调用的示例。这种模式可以复用于：

- 修改装备词条；
- 重新汇总面板；
- 重新计算 DPS；
- 比较新旧结果。

### 8.4 具备回归校验工具

现有验证脚本可以用于后续保证：

- 引擎重构没有改变已验证的旧结果；
- 新增属性不会破坏已有流派；
- 修改公式时可以定位差异。

## 9. 与完整产品设想的主要差异

### 9.1 当前没有装备实体和词条模型

当前输入的是最终面板，不是：

```text
左武器、右武器、环、佩、冠胄、胸甲、胫甲、腕甲
+ 初始词条
+ 4 条调律词条
+ 定音词条
```

因此当前引擎无法独立回答：

- 这件装备在哪个部位；
- 装备是多少等阶；
- 哪个词条对应哪个属性；
- 词条是否属于该部位的合法候选池；
- 4 条调律词条是否重复；
- 定音词条是否独立；
- 装备是否为草稿或完整数据。

### 9.2 当前没有完整角色属性汇总器

当前没有一个模块明确负责：

```text
固定属性
+ 流派半固定属性
+ 8 件装备词条属性
= 引擎所需的最终面板输入
```

现有流派包中虽然有不少固化数值，但它们目前更像“已抽取完成的流派战斗配置”，并不等同于我们之前讨论的完整养成属性来源模型。

需要进一步确认：

- 哪些数值确实属于流派方案；
- 哪些数值属于心法、套装、武库、弓玦或武学天赋；
- 哪些数值应该随玩家输入而变化；
- 哪些数值可以固定取满。

### 9.3 当前流派选择是文件选择，不是产品层面的选择

当前需要通过命令行指定流派 JSON：

```text
--liupaibao packages/pozhu_zun_3.5.json
```

未来如果做产品界面，应增加：

```text
用户选择流派
→ 自动匹配流派包
→ 加载对应半固定属性
→ 进行完整角色计算
```

此外还需要定义流派版本、游戏版本和混搭方案的关系。

### 9.4 当前战斗轴固定在流派包中

当前每个流派包自带一套排轴和战斗时间。这样做适合复现某个固定计算器，但完整产品可能需要支持：

- 不同武学组合；
- 不同技能循环；
- 不同技能轴；
- 不同目标；
- 不同副本天赋；
- 不同战斗时间；
- 多个场景预设。

因此需要区分：

```text
流派默认轴
用户选择轴
用户自定义轴
```

不能默认认为所有玩家都使用同一个轴。

### 9.5 当前没有装备替换报告

当前引擎只返回最终结果，没有现成接口告诉用户：

- 哪些属性发生变化；
- 哪些词条造成了变化；
- DPS 变化来自哪个乘区；
- 是属性提升、增伤提升、穿透变化还是状态占比变化；
- 是否跨过了某个门槛或阈值。

### 9.6 当前没有最优 8 件组合搜索

当前没有：

- 装备库存；
- 按部位分组；
- 候选池筛选；
- 组合空间搜索；
- 剪枝；
- 支配关系排除；
- 推荐组合；
- 当前组合与最优组合的对比。

## 10. 当前代码中值得讨论的具体问题

以下问题不是本调研结论的最终判断，仅作为后续逐项讨论清单。

### 10.1 外功最小值大于最大值

破竹樽输入中存在：

```text
最小外功 = 4473
最大外功 = 3417.6
```

引擎已经实现了对应的特殊规则：这种情况下会固定按最小值计算。

需要确认：

- 这是游戏真实机制还是某个数据录入特点；
- 这个值是否代表“最小值和最大值已经发生交叉”；
- 外部属性汇总层是否应允许这种状态；
- 是否需要在界面上明确提示；
- 是否应对所有相关分支统一处理。

### 10.2 `waigong.shanghaiJiacheng = null`

当前外功伤害加成字段固定为 `null`，因为外功伤害加成基准放在流派包中。

需要讨论：

- 这个字段是否应该保留；
- 是否应该完全从输入 schema 中删除；
- 是否需要记录它来自哪个配置来源；
- 未来用户自定义时是否允许覆盖流派基准。

### 10.3 输入缺少正式 schema 校验

当前大量使用 `float()` 和字典下标，尚未看到完整的计算前校验。

可能需要检查：

- 必填字段；
- 数值范围；
- 施放序号；
- 战斗时间是否大于 0；
- 增益名称是否存在；
- 结算范围是否越界；
- 四态比例是否合理；
- 流派包与输入快照版本是否匹配。

### 10.4 未知增益的处理

当前代码中对于战斗轴引用的未知增益似乎会进行过滤，而不是直接报错。

需要确认：

- 未知增益是否应该按 0 处理；
- 是否应该标记配置缺失；
- 是否应该让整次计算失败；
- 哪些字段允许兼容旧数据，哪些字段必须严格校验。

### 10.5 结算施放的边界规则

当前结算施放支持范围引用和二次伤害，但没有看到完整的边界校验，例如：

- 范围是否包含自身；
- 范围是否越界；
- 是否存在重复或循环结算；
- 结算比例是否允许超过 1；
- 结算顺序是否完全等价于游戏。

### 10.6 百分比的存储与范围

当前数据以小数存储，例如：

```text
32% → 0.32
8.47% → 0.0847
```

需要进一步定义每类字段的合法范围和类型：

- 概率；
- 增伤；
- 减伤；
- 穿透；
- 直接率；
- 目标属性；
- 负值增益。

### 10.7 计算结果版本追踪

当前默认结果没有完整记录：

- 游戏版本；
- 流派包版本；
- 输入快照版本；
- 公式版本；
- 目标环境；
- 计算场景。

后续建议保存完整计算快照，避免游戏更新后历史结果失去解释。

### 10.8 ADPS 与毕业率的职责

当前：

```text
ADPS = 总伤 / 战斗时间
毕业率 = ADPS / 流派包基准
```

需要进一步确认产品上的定位：

- 装备比较是否只使用 ADPS；
- 毕业率是否只作为原 Excel 的辅助指标；
- 不同流派包的毕业率是否绝不横向比较；
- 界面是否显示基准来源和适用场景。

### 10.9 固定轴与真实 DPS 的关系

当前模型更像：

> 在指定技能轴、指定目标和指定时间内的期望 ADPS。

这不必然等于：

> 任意实际战斗中的真实平均 DPS。

需要和后续产品设计一起明确：

- 轴的来源；
- 轴是否允许用户修改；
- 轴的时间是否固定；
- 不同技能轴是否应该分别计算；
- 是否需要给多个场景建立推荐。

### 10.10 五种伤害分支与“生效武学属性”的关系

当前代码允许五种分支同时有输入值，并由生效武学属性决定哪一支使用属性倍率和属性固伤特殊系数。

这可能与游戏机制有关，也可能只是对原始 Excel 的建模方式，需要结合实际机制进一步确认，不能只根据字段命名下结论。

## 11. 建议的后续分层架构

当前可以继续保留 `dmg-engine` 的核心计算代码，并在其上增加产品层：

```text
游戏静态数据
（等级、世界突破、天赋、蹊跷、叠音、流派、词条池、等阶区间、技能倍率等）
                         ↓
角色属性模型
（固定属性 + 半固定属性 + 装备词条属性）
                         ↓
装备数据层
（8 个部位、装备等阶、初始/调律/定音词条）
                         ↓
面板构建器
（转换为 DPS 引擎输入快照）
                         ↓
现有 DPS 引擎
                         ↓
单件替换比较 / 最优 8 件组合搜索
```

建议新增的职责大致包括：

### 11.1 属性模型

定义：

- 属性名称；
- 属性类型；
- 加法、百分比、穿透、抗性等类别；
- 来源；
- 数值上下限；
- 叠加规则；
- 是否依赖装备等阶；
- 是否依赖场景。

### 11.2 装备模型

定义：

```text
装备
├── 部位
├── 等阶
├── 初始词条
├── 调律词条 × 4
└── 定音词条
```

同时定义各部位可出现的词条池和重复规则。

### 11.3 角色面板构建器

输入：

- 固定属性配置；
- 流派方案；
- 当前装备集合；
- 游戏版本。

输出：

- 完整属性面板；
- 引擎可直接使用的输入快照；
- 每项属性的来源和贡献。

### 11.4 比较器

输入：

- 当前装备组合；
- 候选装备；
- 场景配置。

输出：

- 替换前后面板；
- 替换前后 DPS；
- 差值和百分比；
- 关键变化项；
- 推荐结论。

### 11.5 组合搜索器

输入：

- 各部位候选装备；
- 锁定和排除条件；
- 场景配置。

输出：

- 最优 8 件组合；
- 当前组合与最优组合的差值；
- 搜索方式和候选规模；
- 是否为穷举或近似搜索。

## 12. 初步优先级

建议先讨论并确认以下顺序：

### 优先级 A：先明确游戏机制

1. 当前 `dmg-engine` 的五种伤害分支是否完整；
2. 最小外功大于最大外功是否为真实机制；
3. 穿透正负的伤害公式；
4. 会心、会意、精准、擦伤的实际关系；
5. 定音、特定增伤、特殊增伤和结算增伤的准确口径；
6. 固定轴是否适用于目标产品；
7. 目标、抗性和世界突破抗性的使用范围。

### 优先级 B：再明确属性模型

1. 固定属性的准确来源；
2. 半固定属性中每个来源的边界；
3. 装备词条如何转换为面板属性；
4. 不同词条的叠加方式；
5. 8 个部位的词条池；
6. 装备等阶和数值区间；
7. 抗性属性是否进入单人 DPS 计算。

### 优先级 C：最后设计产品功能

1. 流派选择；
2. 当前装备录入；
3. 候选装备录入；
4. 单件替换；
5. 装备贡献解释；
6. 最优 8 件组合；
7. 多场景比较；
8. 数据版本和历史结果。

## 13. 调研结论的适用边界

本记录基于对当前目录中代码和 JSON 的阅读，不代表以下事项已经完成验证：

- 游戏官方机制；
- 原始 Excel 之外的实战伤害；
- 不同流派的所有差异；
- 当前输入值的来源正确性；
- 所有词条的真实属性范围；
- 所有抗性和世界突破的计算方式；
- 是否适合直接扩展为多流派、多场景产品。

因此，后续讨论时应优先把“当前实现事实”和“游戏机制判断”分开：

```text
代码实际做了什么
数据里实际填了什么
游戏真实规则是什么
产品最终想模拟什么
```

这四者可能并不完全相同。

---

## 14. 当前最重要的一句话

> `dmg-engine` 目前已经解决了“在特定流派包和特定战斗轴下，根据一组最终面板输入计算期望 ADPS”的问题；它尚未解决“如何把玩家的养成属性和 8 件装备词条转换为这组最终面板输入”的问题。

这个判断是当前调研的暂定结论，后续应随着逐项讨论不断修正。
