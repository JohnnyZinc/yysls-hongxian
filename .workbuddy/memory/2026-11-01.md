# 2026-11-01 处置建议层（P2）设计定稿

> 承接 10-31 起的长讨论：重新梳理"录入一件装备 → 给品阶 + 处置"。结论已写入 `评价系统设计.md` **§11**，本文只记决策依据与实测数据。

## 定稿要点

1. **只评价当前这一件**，参照物是"方案标准"和"当前整套配置"，不引用第二件装备。文案禁止"比…好/差"，只说"穿上后本套 DPS ±x%"。被替换的旧件由玩家在背包单独点开评价（case5 就在这个入口）。　⚠ **本条已被当日「处置文案改口语化」推翻**：现允许"比你现在穿的那件更好"，改用完整人话（见文件末尾同名小节）。
2. **处置四分类**：直接穿上 / X转律为Y后穿上 / 放背包 / 分解回收。另有「信息不足，无法判断」= 拒绝回答，不是第五类。
3. **规则链有序**（先命中先返回）：空位→直接穿上；`Δ转后`超死区且>Δ现状→转律后穿上；当前档>已穿档→直接穿上；同档且Δ现状超死区→直接穿上；档∈{天,地}→放背包；其余→分解。
4. **档位优先 = 配额优先**：天地玄黄就是 (k,m) 字典序，不是两套标准。**DPS 是第二层，只在同档破僵局**——用户反复强调 DPS 引擎不精确、配额才最准。
5. **DPS 的真正意义**（用户原话意）：玩家大多数时候穿地/玄/黄、且这个阶段持续数月；两件玄档 k/m 相同 → 配额排不出 → 只能靠 DPS 给个结论，**哪怕结论可能是错的，也比让玩家纠结好**。所以"玄黄是主力场景，DPS 破僵局是最高频路径"，死区不能设太大。
6. **天/地不吃 DPS**：天档不可再生、DPS 低可修复（承音抬数值、其他部位换玄黄补三率）。用整体短板否定局部 = 归因错误。⇒ case2「更好但 DPS 降 → 留背包」**反转**为"档位更高就穿"。
7. **地档也放背包**（推翻 DETAILS 旧句"地/玄/黄一律不给收藏建议"）。**放背包大概率是同档候补**，不是低一档候补。
8. **转律**：前/后分开评级（`tierAfter` 只是潜力，禁止渲染成当前天阶）；CD 装备级、可重转、成本低 ⇒ 每件独立判断，不做跨件分配；**门槛改为 `Δ转后 > Δ现状`**。
9. **跨方案冲突不调和**：改为提问"这件打算给哪个方案用"，归属默认取 `configsUsingPiece`。
10. **全局搜索**（未实现）：当前配置 8 槽 × 整个装备库（含已穿件）；判据同 §11.5（配额优先、同档 DPS 决胜）；每件取"原样/最优转律后"两态一起进搜索（避免"先搜索后转律"的循环依赖）；比较单位是**装备集合**不是槽位；剪枝在**纯计数层**（不跑 panel/dps）⇒ 可穷举全解、能证明"已是最优"；提示用标记不弹窗。

## 实测反例（破竹风·大外流·胫甲，承音值口径，真实引擎跑出）

当前基线：8 件、胫甲为玄档（带气血），DPS = 100,197，配额缺会心 1。

| 候选件 | 当前档 | Δ现状 | 转律后 | Δ转后 | 结论 |
|---|---|---|---|---|---|
| 劲+[大外,劲,首领,会心] | 天 | +3.16% | — | — | 直接穿上 |
| 劲+[大外,劲,首领,势] | 天 | +1.29% | — | — | — |
| 劲+[大外,劲,首领,外功防御] | 玄 k=1 | 0.00% | 外防→势 天 | **+1.29%** | **转律后穿上** |
| 劲+[大外,会心,首领,势] | 地 m=1 | **+3.28%** | 会心→劲 天 | +1.29% | **直接穿上，禁止转律** |

- 最后一行是**旧门槛的致命反例**：转后到天，但 DPS 掉 2pp。旧 `adviseConversion` 门槛 `tierAfter==='天'` 会给出负收益建议。
- 规律：**救废型（k↓）必然正收益**（无效词条贡献≈0）；**补缺型（k 不变、m↓）可能为负**，必须过 DPS 关。
- 另一实测：冠胄部位的天档已饱和（validSet 只有 5 种词条、5 个位），任何天档冠胄互为等价物 → 该部位"放背包"是常态，不是异常。

## 顺带记录的游戏机制（用户补充）

- 词条出现概率未公布，但体感有用词条（大外/小外/劲/敏）概率低，垃圾词条（气血最大值/外功防御/体/御）对所有方案无用，属性攻击跨系无用；系统**刻意制造冲突**（小外+劲、大牵丝+大裂石）⇒ **玄/黄出现率极高，天/地很少**。
- 冲突组合**不需要枚举展示**（用户定：会非常多且对决策无用）。
- 转律可重转，每次转后 3 天 CD，材料成本不高。

## 补：武器桶模型（同日追加，为鸣金霆=双枪）

- **触发**：下版本将上线「鸣金霆 = 两把枪」。现有代码隐含「武器类型 = 装备身份」（单射），双枪变多射 → 多处静默出错。
- **实测（合成双枪配额：剑增1→枪增2、大外12→11）**：配额层完全正常（两槽各得 `[1大外, 1枪武学增伤]`、`weaponTypes={武器1:枪, 武器2:枪}`）；但 `sameEquipKey(两把枪)=true` → `evaluateSwap` 替换后件数 **2→1**、结论反向为「保留旧件」，且不报错。
- **定稿模型**：武器按类型**分桶**，桶容量 = 该类型在 `_meta.json.武器` 出现次数。桶内无序，`武器1`/`武器2` 只是存储位置。**替换 = 遍历桶内各件试换、取 ΔDPS 最优者为被替换者**（比一把好换它 / 都更好换最差 / 都更差丢弃）。
- **`gearAfter` 必须按索引移除**被选中那件，不能 `filter(sameEquipKey)`。
- **前提自适应**：桶语义要求两槽 `required` 相同 → `derivePrescription` 输出「槽位等价」布尔；false 时按指定槽评档（跨槽取最优会虚高）。
- **单件定位用 `uid`**（`state.pool` 已有），不引入 slotKey。
- **否决「固定槽位」**：双枪固定后两槽都合法仍分不清；错型混放由桶按类型收件天然挡住。
- **未决**：鸣金霆配额到底是「枪增2条」还是「枪增1条（主副手有别）」——版本未上线无法确定，故代码自适应，不赌。
- 已写入 `评价系统设计.md` §12，DETAILS.md「武器槽模型」节，MEMORY.md 红线第 7 条。

## 修正：转律目标该转成什么（用户报的真实案例）

**现象**：牵丝玉·走地玉·大外流，6 件已穿 + 一把伞（初始大外 / 调律[伞增, 大外, 小外, 会心]），只差胸甲。工具建议「小外→敏」，但正确应是「小外→劲」。

**根因**：`adviseConversion` 把 DPS 放在排序第一位。转劲与转敏都升天、缺口都剩 5，敏的 DPS 高 0.9pp ⇒ 敏胜。但**只有转劲**能让剩下的胸甲补齐配额（劲缺 2，胸甲初始池不出劲、调律又不能重复 ⇒ 胸甲最多 1 条劲）。

**修法**：
1. `quota.js verifyItemFits` 修武器：原先 `mergedSlots['武器']` 不存在直接 return null（武器从不做全局复核）。现按 `weaponType` 定位绑定槽，双枪两槽都试。
2. 新增 `verifyGearFits(prescription, gear)`：钉住**一批**已穿件，其余空槽自由填充，判能否恰好配满（最大流）。这才是"该转成哪条"的正确判据——差别不在缺口数，而在剩余空位塞不塞得下。
3. 转律排序改为 **可行性 → 必修 → 缺口 → DPS**；`必修 = 有空槽 && 转后可行 && 转前不可行`（DPS 不涨也要转）。**8 件已满时不判必修**，否则会把"拆东墙补西墙"（D1 地档缺劲件 +3.28%→+1.29%）也判成必修。
4. `dispose.bestConversion` 同口径；规则 1 接受"必修"；UI 文案在必修时显示「补齐配额必需」而不是 DPS 涨幅。

**验证**：`test_conversion` 新增场景 J（4→5 项，共 43），全量 `npm run test:all` 全绿（UI 279）。

## 修正二：转律目标的合法范围（用户第二例）

**现象**：同 6 件 + 伞（初大外 / [伞增, 外功防御, 小外, 会心]），工具建议「外功防御 → 会意率」，而本方案配额里根本没有会意率。

**根因两条**：
1. 转律候选只看"是否救废（k↓）"，没看**目标是否被配额需求**。会意率在该槽自由集里（合法）但不在配额行里 ⇒ 转了不减少任何缺口，只是把废词条换成另一条零贡献词条，k 从 2→1、DPS 微涨，于是被选中。
2. 实测还发现第二个洞：有废词条时会建议**转掉有效词条**（会心→大外），废词条留着。

**修法**：
- 新增 `quota.demandAffixesOf(prescription)` = 配额行 any_of 并集；转律目标必须在其中（advisor / dispose 同步）。
- 新增硬约束：`cur.k > 0 && from ∉ 无效调律 ⇒ 跳过`（先废后有效）。
- `test_conversion` 场景 K 锁定（4 项：有建议 / 目标全在需求集 / 不出现会意率 / from 只能是两条废词条之一）。

**修后表现**（复现的那套）：建议「小外→敏」缺口 7→6 —— 敏在配额内，属合法目标；该套 7 条缺口而只剩胸甲 5 个位，任何单条转律都补不满，故在同等缺口内由 DPS 决胜。

## 修正三：转律试算的数值口径（用户第三例，最严重）

**现象**：同 6 件 + 伞（初大外 / [伞增, **外功防御**, **小外**, 会心]）。工具建议「小外→敏 +2.05%」优先于「外防→敏 +1.72%」。用户判断反了：小外参与 DPS、外防完全不参与，保留小外的方案必然更高。

**根因**：`adviseConversion` 的 `mkTrial` 只改 `属性`、**沿用原位置的 `数值`**：
- 小外(承音 131.2) → 敏，敏被当成 131.2（虚高 58%）
- 外功防御(承音 65.612) → 敏，敏被当成 65.6（虚低 21%）⇒ 被压了 21%，所以看起来更差

正确取值（敏承音 83.1）下完全反过来：

| 候选 | 沿用原数值 | 按目标重取 |
|---|---|---|
| 小外→敏 | +2.04% | +0.93% |
| 外防→敏 | +1.71% | **+2.12%** |

**修法**：`quota.derivePrescription` 返回 `_affixes`（原始词条表引用）；`advisor.adviseConversion` 加 `retune()`，逐位比较词条名，**变了才按目标词条重取承音值**（同名则保留玩家实测值，不覆盖）；接受 `opts.affixes` 覆盖。`dispose`/`search` 本就走 `transformedItem`，无此问题。

**附带发现**：外防→敏(+2.12%) > 外防→大外(+1.18%) 的主因**不是攻击数值，是五维达标率 0.9557→1.0**——一条敏同时补足敏捷，天赋乘区不再被缩放。面板侧小外 2390.8→2471.3（敏×0.9 进小外）、大外 5356 不变。用户"转大外应该更高"的直觉在这一点上不成立，属模型机制而非误差。

**验证**：`test_conversion` 场景 L（5 项）：首选必须是外防→敏；Δ 必须等于"按目标重取"的实算值；并断言沿用旧口径会更低（防回归）。全量 **662 项全绿**（引擎 12/11/44/45/47/**52**/42/21/20/29/21/16/21 + UI 279）。

**待办（用户明确说暂不加）**：转律**升不到天/地阶时不该建议**（避免浪费材料）。当前两个废词条 ⇒ 转掉一条只到玄，仍会给建议。等用户确认后再加门槛。

## 收口：全局复核的两处重复文案

同一事实（`globalFitVerified === false`）被显示了两遍：档位行的「⚠ 全局复核未通过」+ warnings 里「结构档位达标，但其余 7 部位无法补齐配额（局部必备/自由是必要条件…）」。后者还有两处毛病：「结构档位达标」在黄档是错的（实测黄档 24080 组全部未通过）、括号里是实现原理不是玩家信息。

改成一句：`无效词条 N 条 · 缺必备 M 条 · ⚠ 其余部位补不齐配额`，且**仅档位玄及以上显示**（黄档恒定未通过 ⇒ 无信息量；通过时也不显示 ✓）。warnings 那条已从 `advisor.js` 删除，`globalFitVerified` 字段保留供 dispose/search 消费。`test_studio` 加两条防回归断言（281 项）。

## 整合：背包件详情从五块并成三段

**问题**：详情页并列五块（处置 / 换装对比 / 匹配度明细 / 转律建议 / 跨方案），其中三处是同一条事实说两遍：

## 转律「换洞」问题（玩家实测，裂石钧·纯唐轴·小外流）

**现象**：8 件里只有胫甲缺敏（地档，m=1），提示「把「最小外功攻击」转成「敏」」——而小外是**本槽必备**。转完 m 还是 1（洞从敏挪到小外），玩家照做只会换来另一个缺口。正确做法是等一个更好的环。

**根因（两层，都是"只看聚合数"）**：
1. 只看 `m` 总数：必备缺口从 [敏] 变成 [小外]，m 不变 ⇒ `结构不可退化` 放行。
2. 只看缺口总数：敏 −1、小外 +1，总数不变；但 `relief` 只看"有没有行变小"，敏那行变小就被判成「全局必需」。

**修法**：
- `advisor.noNewRequiredGap(before, after)`：按词条身份比必备缺口，任一条变多即否决。`dispose.bestConversion` 与 `adviseConversion` 都接。
- `advisor.noRowWorse(beforeRows, afterRows)`：配额行级 Pareto，任何一行缺口不许变大；`缺口改善` 改为「总数变小 **且** 行级不劣」。
- `test_conversion` 场景 N（6 项）：N1 锁"m 不变"，N2 锁换洞被否，N3 锁转掉多余会心仍允许，N4/N4b 锁"不是一刀切不给 + 不给转必备"，N5 锁首选不是小外→敏。

**验证**：`npm run test:all` 全绿（`test_conversion` 52→59，UI 293，0 失败）。
